# 当たり判定のしくみ

このプロジェクトで使った当たり判定の技術を、ゼロから説明したもの。
プログラミングの経験はあるけれど当たり判定は初めて、という人を想定している。

数式はほとんど出さない。かわりに「なぜそうなっているのか」を書く。

---

## 0. 一番大事な前提：見た目と当たり判定は別物

ゲームの中の物体は、**2つの体を持っている**。

- **見せるための体**：画面に描かれる形。細かくて、綺麗
- **ぶつけるための体**：当たったかどうかを計算するためだけの形。粗くて、単純

この2つは一致していない。むしろ**一致していないのが普通**。

このプロジェクトで「判定表示」をONにしたときに出てくる線が、後者だ。ピンクのドーナツの周りに、ドーナツより大きな球の線が出る。見えている穴は、ぶつけるための体には存在しない。だから通れない。

初心者がつまずくのはここで、
「見えているのに当たらない」「何もないのに当たる」というバグは、**たいていこの2つがズレていることが原因**だ。

### なぜわざわざ分けるのか

計算量のため。

画面に出ているドーナツは、三角形が数百枚集まってできている。相手も数百枚だとすると、真面目に「どの三角形とどの三角形が重なっているか」を調べると、数百 × 数百 = 数万回の計算になる。物体が50個あれば、その組み合わせがさらに掛かる。1秒間に60回これをやるのは無理だ。

一方、球と球が重なっているかどうかは、**引き算と掛け算が数回**で終わる。

だから、見た目は細かく作って、当たり判定は「だいたい同じ形の、計算が速い形」で代用する。これが当たり判定の出発点にある割り切りだ。

## 1. 判定に使う形と、その計算のしくみ

速い順に並べる。実際のゲームは、この中から物体ごとに適した形を選ぶ。

### 球（一番速い）

2つの球が重なっているかは、**中心どうしの距離**を測るだけでいい。

```
中心の距離 < 半径A + 半径B  なら、重なっている
```

回転しても形が変わらないので、向きを一切考えなくていい。これが球が圧倒的に速い理由だ。

弾、コイン、丸っこいキャラクターはだいたい球で済ませる。

> このプロジェクトでは、青い球の敵と、発射される弾に使っている。
> あとは「細い棒なのに判定は大きな球」というズレ体験にも使っている。

### 軸に沿った箱

傾いていない箱どうしなら、**X・Y・Z の3方向それぞれで、範囲が重なっているかを見る**だけでいい。

```
Xの範囲が重なっている？ かつ
Yの範囲が重なっている？ かつ
Zの範囲が重なっている？   → 3つ全部Yesなら重なっている
```

1方向でも重なっていなければ、その時点で「当たっていない」と確定できる。とても速い。

傾かない箱のことを **AABB** と呼ぶ（Axis-Aligned Bounding Box、軸に沿った囲み箱）。後で出てくる「ざっくり調べる工程」でも主役になる。

### 傾いた箱、多面体

箱が回転していると、上の方法は使えない。

ここで使われる考え方が、**「1枚の板で2つを仕切れるなら、当たっていない」**というもの。

紙に2つの図形を描いて、間に直線を1本引けるなら、その2つは重なっていない。逆に、どう線を引いても必ずどちらかを横切ってしまうなら、重なっている。3Dなら線ではなく板（平面）になる。

調べるべき板の向きは無限にあるように見えるが、実は**それぞれの図形の面の向きと、辺どうしの組み合わせ**だけ調べれば十分だと分かっている。だから有限回で終わる。

この考え方を **分離軸判定**（Separating Axis Theorem）と呼ぶ。箱、三角形、多角形など、へこみのない形どうしに使える。

### へこみのない形（凸包）

「へこんでいない形」のことを **凸形状** と呼ぶ。輪ゴムをかけたときに、輪ゴムが形にぴったり沿うなら凸。どこかが浮くならへこんでいる。

へこんでいない形は、分離軸判定や、それを一般化した手法で扱える。**へこんでいる形は扱えない**。これが当たり判定の世界で一番大きな制約だ。

だから、へこんだ形を扱いたいときは **へこんでいない形を複数組み合わせる**。人型キャラなら、胴体に1つ、腕に2つ、脚に2つ、というふうに。

> このプロジェクトのジェム（水色の多面体）がこれ。点をいくつか置いて、それらを包む最小のへこみのない形を自動で作らせている。これを **凸包** と呼ぶ。
> 雪だるまとダンベルも同じ考え方で、球2個や球2個＋円柱を1つの物体として扱っている。

### カプセル、円柱、円錐

カプセルは「線分から一定距離以内の空間」と定義できる。だから判定は、**線分と線分の最短距離を測って、半径の合計と比べる**だけ。球の判定をちょっと拡張したもので、かなり速い。

人型キャラの当たり判定にカプセルがよく使われるのは、これが理由。速いうえに、角がないので地形に引っかかりにくい。

円柱と円錐は専用の計算が用意されている。カプセルより少し重い。

### 三角形の集まり（形そのまま）

見た目のデータをそのまま判定に使う方法もある。三角形を1枚1枚持っておいて、当たりそうな三角形だけを調べる。

これなら**へこんだ形も、穴が空いた形も、正確に扱える**。このプロジェクトの水色のドーナツが穴をくぐれるのは、これを使っているから。

ただし制約が大きい。

- **重い**。三角形の枚数だけ計算が増える
- **薄い**。三角形には厚みがないので、速い物体が通り抜けやすい
- **動かせない**。この形は「重さの分布」を計算できないので、物理で転がしたりできない

だから用途はほぼ**地形専用**だ。床、壁、階段、坂。動かないものにだけ使う。

> このプロジェクトのドーナツが固定されているのは、仕様がそう決めたからではなく、**動かせないから**だ。

## 2. 総当たりを避ける工夫

物体が50個あると、組み合わせは 50×49÷2 = 1225 通り。全部を正確に調べると重い。

そこで、**2段階に分ける**。

### 1段階目：ざっくり

すべての物体を、とりあえず**傾いていない箱**で囲む。そして「箱どうしが重なっていない組み合わせ」を捨てる。

箱の判定は数回の比較で終わるので、1225通りでも一瞬だ。そして実際に近くにいる物体は数組しかないので、ここでほとんどが消える。

さらに、空間を区切って管理したり、木構造で整理したりして、1225通りすら調べずに済ませる工夫もある。

これを **ブロードフェーズ**（大まかな工程）と呼ぶ。

### 2段階目：正確に

1段階目で残った数組だけを、本来の形で正確に調べる。球なら球として、多面体なら多面体として。

これを **ナローフェーズ**（詳しい工程）と呼ぶ。

> この2段階構造は、自作するときにもそのまま使える。
> まず全部にAABBを付けてふるいにかけ、残ったものだけ本気で調べる。

## 3. 当たった「あと」どうするか

ここからが「衝突応答」の話。当たったかどうかを知るのと、当たった結果どうなるかは、まったく別の問題だ。

### 重なりを解消する

判定は1秒に60回など、**飛び飛びの時間**で行われる。だから気づいたときには既に少しめり込んでいる。

そこでナローフェーズは、「当たった／当たっていない」だけでなく、次の3つを返す。

- **どこで**当たったか（接触点）
- **どっち向きに**押し返せばいいか（法線、めり込みが一番浅くなる方向）
- **どれだけ**めり込んでいるか（深さ）

この3つがあれば、「この向きにこれだけ押し戻せば重なりが消える」が分かる。

### 押し返す強さを決める

単に位置をずらすだけだと、物体が震えたり、突然ワープしたように見えたりする。そこで多くの物理エンジンは、**位置ではなく速度を変える**。

考え方はこうだ。

> 2つの物体が近づいている。このまま行くとめり込む。
> ならば、めり込まない速度になるように、両方に力を加えればいい。

このとき**重さ**が効いてくる。軽いものは大きく弾かれ、重いものはあまり動かない。これは自動的にそうなる。同じ力を加えても、軽いほうが速度の変化が大きいからだ。

> このプロジェクトで、敵にランダムな力を加えるときに**重さを掛けている**のはこのため。
> 掛けないと、軽い球だけが吹っ飛んで、重いダンベルはほとんど動かない。

### 全部同時に解けない問題

物体が積み重なっていると、1組ずつ押し戻しても解決しない。Aを押すとBにめり込み、Bを押すとCにめり込む、という連鎖が起きる。

そこで実際の物理エンジンは、**全部の接触を何度も繰り返し調整する**。「少しずつ全員を押し戻す」を数回繰り返して、だいたい落ち着いたところで打ち切る。

完全に正解を出しているわけではない。だから物が少し沈んだり、震えたりする。これは手抜きではなく、現実的な妥協だ。

## 4. 物体の3つの種類

物理エンジンには、性格の違う3種類の物体がある。**これを理解していないと事故る。**

| 種類 | 動くか | 押し返されるか | 使いどころ |
|---|---|---|---|
| **動く物体** | 力や重力で動く | される | プレイヤー、箱、ボール |
| **動かない物体** | 絶対に動かない | されない（相手だけ動く） | 床、壁、地形 |
| **位置で動かす物体** | 書いた位置に必ず行く | **されない** | 動く床、回る障害物、エレベーター |

3つめが曲者だ。これは「絶対にこの位置に来い」と命令される物体なので、**何があっても止まらない**。相手を押しのけて進む。壁も無視して通り抜ける。

> このプロジェクトの「すり抜け」ボタンは、プレイヤーをこの3つめに切り替えているだけ。
> それだけで壁も敵もすり抜けるようになる。

そして、これは**初心者が最初に踏む定番のバグ**そのものだ。

「キャラを動かしたい」→「座標を直接書き換えればいいか」→「壁をすり抜けた」

物理エンジンを使っていても、位置を直接代入して動かすと同じことが起きる。当たり判定は位置を代入したあとに行われるので、**移動の途中は誰も見ていない**からだ。

正しくは、位置ではなく**速度や力を与えて**、移動そのものを物理エンジンにやらせる。

> このプロジェクトのプレイヤーは、通常時は速度を与えて動かしている。
> だから壁で止まるし、敵にぶつかられると押される。

## 5. 当たっても止めない判定

「重なったことは知りたいが、押し返してほしくはない」という場面がある。

- アイテムの取得範囲
- ダメージ判定
- 「この部屋に入ったらイベント発生」のトリガー
- 敵の索敵範囲

このために、**当たり判定として計算はするが、押し返しはしない**という設定がある。呼び名はエンジンによって違うが、センサー、トリガー、などと呼ばれる。

> このプロジェクトの「検知のみ」ボタンがこれ。
> ONにすると全部すり抜けるが、通り抜けた瞬間にちゃんと光る。検知はできている。

自作するときも、この2つは分けて設計したほうがいい。「重なりを検出する処理」と「重なりを解消する処理」を分けておくと、後者を呼ばないだけでセンサーになる。

## 6. すり抜け問題

一番厄介な問題がこれ。

判定は飛び飛びの時間で行われる。1秒に60回なら、判定と判定の間は 1/60 秒ある。

もし物体が 1/60 秒で 2メートル進み、壁の厚さが 10センチだったら？

```
判定した瞬間：壁の手前2メートル   → 当たっていない
次に判定した瞬間：壁の向こう側    → 当たっていない
```

**一度も当たらないまま通り抜ける。** これがすり抜け（トンネリング）だ。

対策は主に3つ。

**1. 移動の軌跡で判定する**
点で調べるのをやめて、「この位置からこの位置まで動く間に何かに当たるか」を線や掃引形状で調べる。正確だが重いので、弾など一部の物体にだけ使う。

**2. 時間の刻みを細かくする**
1/60 秒を 1/120 秒にすれば、1回あたりの移動距離が半分になる。単純だが、全体が2倍重くなる。

**3. 速度に上限をつける**
そもそも「1回の移動距離が、一番薄い壁の厚さを超えない」ように制限してしまう。地味だが確実で、実際よく使われる。

> 補足：このプロジェクトで検証したところ、使っている物理エンジン（Rapier 0.20）は、
> ざっくり調べる工程で**速度の分だけ囲み箱を膨らませている**ため、
> 秒速520メートルの弾でも8センチの板を貫通しなかった。
> 最近のエンジンは、この問題にかなり強くなっている。
> 詳しい実測値は PROGRESS.md に記録してある。

## 7. 時間の刻み方

すり抜けと関係する、もう一つの落とし穴。

画面の更新に合わせて物理計算をすると、**端末によって物理の速さが変わる**。

最近のスマホは1秒に120回画面を更新する。60回を前提に書いたゲームをそこで動かすと、**物理が2倍速になる**。逆に処理が重い端末ではスローモーションになる。

解決策は、**画面の更新と物理計算を切り離す**こと。

```
経過時間を貯めておく
貯まった時間が 1/60 秒を超えていたら、物理を1回進めて 1/60 秒ぶん減らす
まだ超えていたら、もう1回進める
（1フレームで進める回数には上限を設ける）
```

こうすると、画面が何回更新されようと、物理は常に 1/60 秒ずつしか進まない。どの端末でも同じ速さになる。

上限を設けるのは、タブを切り替えて戻ってきたときなどに「10秒ぶんの物理をまとめて計算しようとして固まる」のを防ぐため。

> このプロジェクトでは `src/main.ts` のループがこれをやっている。

## 8. ゲームらしくするための調整

物理的に正しいことと、遊んで気持ちいいことは違う。実際のゲームでは次のような調整が入る。

**判定は見た目より少し小さく**
プレイヤーが避ける対象（敵の攻撃など）の判定は、見た目より小さめにする。「避けたのに当たった」は理不尽に感じるが、「当たったように見えたのに助かった」は気づかれない。

**プレイヤーの判定は単純に**
プレイヤーは1個のカプセルか箱で済ませることが多い。手足に判定を付けると地形に引っかかって操作感が悪くなる。

**回転を止める**
上から見下ろすゲームのキャラは、たいてい回転をロックしてある。そうしないと、ぶつかった拍子に転がって、どっちを向いているか分からなくなる。

> このプロジェクトのプレイヤーも回転をロックしてある。

**当たったことを見せる**
判定が正しくても、プレイヤーに伝わらなければ意味がない。ぶつかった瞬間に光る、音が鳴る、画面が揺れる。このプロジェクトでは0.2秒だけ白く光らせている。

## 9. このプロジェクトのどこに何があるか

| ファイル | 中身 |
|---|---|
| `src/shapes.ts` | 見た目の形と当たり判定の形を、**ペアで**定義している。ここを分けて書くとズレが混入する |
| `src/objects.ts` | 物体1個ぶんの管理。接触したときの発光もここ |
| `src/props.ts` | 固定物。ドーナツの三角形データの作り方、わざとズラした判定の付け方 |
| `src/player.ts` | 速度を与えて動かす処理と、「すり抜け」モードの切り替え |
| `src/simulation.ts` | 接触イベントを受け取って、誰が誰に当たったかを判別している |
| `src/debugDraw.ts` | 当たり判定を線で描く処理 |
| `src/main.ts` | 時間の刻み方（固定タイムステップ） |

### 見た目と判定を1か所で定義している理由

これは実際に踏みかけた罠なので書いておく。

描画ライブラリと物理エンジンでは、**同じ「サイズ」という言葉の意味が違う**ことが多い。

| 形 | 描画側の指定 | 物理側の指定 |
|---|---|---|
| 箱 | 一辺の長さ | 一辺の**半分** |
| カプセル | 円筒部分の長さ | 円筒部分の**半分** |
| 円柱 | 高さ | 高さの**半分** |

片方だけ間違えると、**見た目の2倍の判定**ができあがる。しかも見た目は正しいので、気づくのに時間がかかる。

だから `src/shapes.ts` では、メッシュとコライダーを必ずセットで返す関数にしてある。呼び出す側は形の名前を指定するだけで、寸法を手で書けないようにしている。

自作するときも、この対策は真似する価値がある。

## 10. 自分でゲームの当たり判定を作るなら

順番はこれを勧める。

**1. 物理エンジンを使うかどうかを決める**

使わなくていいケースは多い。「弾が敵に当たったか」だけなら、**球と球の距離を測るだけ**で終わる。押し返しも重力も要らないなら、物理エンジンは過剰だ。

押し返し、積み重なり、転がり、跳ね返りが要るなら使う。

**2. 見た目より先に、当たり判定の形を決める**

見た目を作ってから判定を後付けすると、必ずズレる。先に「この敵はカプセル」「この岩は凸包」と決めてから、それに合わせて見た目を作る。

**3. 判定を可視化する仕組みを最初に作る**

これは必ず作る。**当たり判定は目に見えないので、可視化しないとデバッグができない**。
「なぜか当たらない」の9割は、可視化すれば5秒で原因が分かる。

**4. 形は単純なものから試す**

最初は全部を球にしてしまっていい。動いてから、必要なところだけ箱やカプセルに変える。
三角形そのままの判定は、地形以外には使わない。

**5. キャラの移動は、位置を直接書き換えない**

速度を与える。位置を代入して動かした瞬間に、当たり判定は無力化される。

**6. 時間の刻みを固定する**

画面の更新回数に物理を合わせない。端末によって速さが変わる。

## 用語のまとめ

読み返すとき用。本文で説明した順に並べてある。

| 言葉 | 意味 |
|---|---|
| コライダー | 当たり判定用の形。見た目の形とは別物 |
| AABB | 傾いていない、軸に沿った箱 |
| 凸形状 | へこみのない形。当たり判定が扱えるのは基本これだけ |
| 凸包 | 点の集まりを包む、へこみのない最小の形 |
| 三角形メッシュ判定 | 見た目の三角形をそのまま判定に使う方式。地形専用 |
| ブロードフェーズ | 全組み合わせをざっくりふるいにかける工程 |
| ナローフェーズ | 残った組み合わせを正確に調べる工程 |
| 接触点・法線・深さ | ナローフェーズが返す3点セット。押し返しに使う |
| 剛体 | 物理エンジンが扱う物体。動く／動かない／位置で動かす の3種類 |
